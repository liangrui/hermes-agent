# Hermes Agent 使用指南 05：记忆系统篇 - 会话管理与上下文维护

## 一、记忆系统概述

### 1.1 记忆系统的设计理念

Hermes Agent 的记忆系统是一个精心设计的模块，专注于解决大语言模型在长对话中面临的核心挑战：上下文长度限制和对话连贯性。传统的对话系统在处理长对话时会遇到两个主要问题：首先，上下文窗口的 Token 数量是有限的，当对话超过这个限制时，新的对话内容会「挤出」旧的内容，导致对话失去连贯性；其次，随着对话的进行，上下文会积累大量无关或冗余的信息，降低了模型对关键内容的关注度。Hermes Agent 的记忆系统通过智能的上下文管理、主动的记忆维护和灵活的存储机制来解决这些问题。它不是简单地保存所有对话记录，而是采用类似人类记忆的工作方式：有策略地保留重要信息、适时地提炼和压缩内容、精准地检索和利用历史数据。

### 1.2 记忆系统的核心组件

记忆系统由几个核心组件构成，各司其职又紧密协作。上下文管理器（Context Manager）是系统的中枢，负责跟踪和管理当前对话的所有内容，包括用户输入、模型输出和工具调用结果。它实时监控上下文的使用情况，在接近限制时触发维护操作。记忆存储（Memory Storage）组件负责持久化存储对话历史，支持多种存储后端，包括本地文件系统、SQLite 数据库和远程存储服务。存储组件还负责索引构建，支持快速的历史检索。压缩引擎（Compression Engine）执行上下文压缩任务，将冗长的对话内容提炼为紧凑的摘要，释放宝贵的上下文空间。检索器（Retriever）根据当前对话的相关性，从历史记忆中提取有用的信息补充到上下文中。策略引擎（Strategy Engine）负责决策何时进行压缩、压缩多少内容以及保留什么信息。

### 1.3 记忆类型与层次

Hermes Agent 的记忆系统采用了分层的记忆模型，类似于人类记忆的工作方式。短期记忆（Short-term Memory）存储当前对话轮次的内容，随着对话进行而不断更新和累积。工作记忆（Working Memory）是当前上下文中活跃的部分，模型在生成响应时可以直接访问的内容，这部分容量受限于模型的上下文窗口。长期记忆（Long-term Memory）存储历史对话的摘要和重要信息，可以跨会话保留，供未来对话参考。这种分层设计使得系统能够在不同时间尺度上处理信息：短期记忆处理即时的对话交互，工作记忆保证当前的生成质量，长期记忆维护跨会话的知识和偏好。理解这个层次结构有助于更好地配置和使用记忆功能。

## 二、会话管理

### 2.1 会话的基本概念

会话（Session）是 Hermes Agent 中的基本工作单元，代表一次完整的对话交互过程。每个会话都有唯一标识符（Session ID）、创建时间、最后活动时间以及关联的元数据。会话具有状态，包括活跃（Active）表示当前正在进行的对话、已保存（Saved）表示已保存但未激活的历史会话、已归档（Archived）表示被移到归档存储的旧会话等状态。用户可以同时维护多个会话，每个会话保存独立的对话历史和上下文状态，便于处理不同的任务或项目。切换会话时，系统会加载对应会话的状态，让你从上次离开的地方继续。这种会话设计支持多任务并行处理，无需在每个任务间做选择。

### 2.2 创建与管理会话

创建新会话是开始新对话的方式，在 CLI 中使用 `new` 或 `/new` 命令即可。创建时会生成唯一的会话 ID，同时你可以为会话指定一个便于识别的名称。会话名称支持中文和特殊字符，应该选择能够描述会话主题或用途的名称，便于后续查找。系统会自动记录会话的创建时间和最后访问时间，这些信息在会话列表中显示。会话可以被重命名，使用 `rename <old_name> <new_name>` 命令。删除会话使用 `delete <session_name>` 命令，但系统会要求确认，因为删除操作不可恢复。归档功能将不常用但需要保留的会话移到归档存储，节省活跃存储空间的同时保留数据。对于需要长期保存的重要会话，可以将其标记为收藏（Favorite），这样即使归档也不会被自动清理。

### 2.3 会话切换与恢复

会话切换让你在多个任务间灵活跳转。使用 `sessions` 命令查看所有已保存的会话列表，包括名称、创建时间和最后活动时间。列表支持排序和过滤，可以按时间、名称或状态筛选。加载特定会话使用 `load <session_name>` 命令，系统会清空当前上下文并加载目标会话的全部历史。加载完成后，你可以继续之前的对话，仿佛从未离开过。如果你想在当前对话中引入另一个会话的内容，可以使用会话引用（Session Reference）功能，通过 `@session_name` 语法将指定会话的相关信息加入当前上下文。临时查看模式（Peek）允许你在不切换的情况下预览会话内容，确认后再决定是否加载。会话恢复机制在异常退出后自动运行，系统会检测并恢复未正常关闭的会话，确保对话不丢失。

### 2.4 会话导出与共享

会话数据可以导出为多种格式，便于存档、分析或共享。导出命令 `export <session_name> [--format <format>] [--output <file>]` 支持纯文本（Plain Text）、Markdown、JSON 和 HTML 等格式。纯文本格式适合打印或简单存档；Markdown 格式保留对话结构，便于阅读和版本控制；JSON 格式包含完整元数据，适合程序处理或迁移；HTML 格式生成可读的网页文件，分享给他人时很方便。导出时可以指定日期范围，只导出部分对话内容。对于团队协作场景，可以使用会话分享功能生成访问链接，接收者可以在只读模式下查看会话内容，但无法修改或继续对话。分享可以设置过期时间和访问密码，增加安全性。导入功能允许将导出的会话重新导入系统，实现跨环境迁移或备份恢复。

## 三、上下文管理

### 3.1 上下文的构成与限制

上下文（Context）是当前对话中所有活跃内容的集合，包括系统提示词、历史对话消息、工具定义和当前输入等。上下文容量受限于所使用模型的上下文窗口大小，不同模型有不同的限制：有的模型支持 4K Token，有的支持 32K，更大的模型甚至支持 128K 或更多。当对话内容接近上下文限制时，系统会发出警告，提示需要压缩或开始新会话。上下文中各个部分占用空间的比例不同：系统提示词通常占用较大比例且相对固定；工具定义占用中等空间；对话历史是主要的可变部分。了解上下文的构成有助于优化使用方式，例如精简系统提示词可以留出更多空间给对话内容。上下文使用情况可以通过 `context` 或 `/context` 命令实时查看。

### 3.2 上下文压缩策略

上下文压缩是管理有限上下文空间的核心技术。当上下文接近容量限制时，压缩引擎会提炼和精简内容，释放空间同时保留关键信息。Hermes Agent 实现了多种压缩策略，默认为智能摘要策略：系统分析对话历史，识别核心主题、关键决策和重要结论，生成简短的摘要替代原始内容。摘要会标注原始内容的索引，方便需要时追溯详情。另一种策略是重要性筛选：系统评估每条消息的重要性分数，保留高分消息，删除或大幅精简低分消息。还有一种策略是固定窗口滑动：始终保留最近 N 轮对话，压缩或丢弃更早的内容。不同的策略适用于不同的使用场景，可以在配置中选择或自定义压缩策略。压缩可以手动触发，使用 `context compact` 命令；也可以设置为自动触发，让系统在适当时机自动执行。

### 3.3 上下文窗口优化

除了压缩，还有其他方法可以优化上下文空间的使用。首先是精简系统提示词，系统提示词是上下文中占用较大且相对固定的部分，可以优化措辞使其更简洁。工具定义的粒度也会影响空间占用，可以只加载当前任务需要的工具，而非全部工具。代码片段和长文本可以只保留关键部分而非完整内容。消息内容的格式化也影响 Token 消耗，去除多余的空行和冗余的格式标记可以节省空间。某些工具可以配置为不将调用结果纳入上下文，只返回简要的结果摘要。定期使用 `context trim` 命令手动清理无用的对话轮次也是好习惯。上下文优化是一个持续的过程，需要根据实际使用情况不断调整。

### 3.4 上下文状态监控

实时监控上下文状态有助于避免意外的限制问题。`context` 命令显示当前上下文的详细状态，包括已使用的 Token 数量、距离限制还有多少空间、各部分（系统提示词、工具定义、对话历史）的 Token 分布。状态栏持续显示上下文使用的大致比例，用颜色提示状态：绿色表示充足，黄色表示接近限制，红色表示即将触发压缩或需要清理。设置使用警告阈值，当上下文使用超过指定比例时主动提醒你进行维护操作。还可以设置自动操作，在上下文达到特定状态时自动触发压缩或提醒。历史监控记录上下文使用的历史趋势，帮助你了解使用模式并优化配置。了解上下文状态是高效使用 Hermes Agent 的关键。

## 四、长期记忆与知识管理

### 4.1 长期记忆的概念

长期记忆（Long-term Memory）是跨会话持久化的知识存储，它使 Agent 能够记住用户偏好、项目背景、重要决策和学到的信息。与短期的对话历史不同，长期记忆中的内容不会随着会话结束而丢失，而是在后续会话中可以主动检索和利用。长期记忆的设计理念是构建 Agent 的「个人知识库」，积累对用户有价值的持久化信息。这些信息包括：用户的工作领域和偏好设置、项目的技术栈和架构决策、常见问题及其解决方案、学到的新概念和术语解释等。长期记忆不是简单的对话存档，而是经过提炼和组织的高价值信息，比原始对话内容更加结构化和易于检索。

### 4.2 记忆的创建与维护

记忆的创建可以通过多种方式进行。最直接的方式是显式存储，通过命令或工具将重要信息标记为长期记忆，例如「记住我偏好使用 Python」或「这个项目使用 React 前端」。Agent 也可能主动建议存储某些信息，当你提到重要偏好或做出关键决策时。自动提炼是另一种创建方式，系统会分析对话历史，识别值得长期保留的信息并建议存储。记忆维护包括定期审视、更新和清理，确保记忆的时效性和准确性。过时的记忆应该被更新或删除，不再相关的信息应该被归档或移除。记忆的标签和分类有助于组织管理，可以使用 `memories` 命令查看和管理已存储的记忆。

### 4.3 记忆检索与利用

存储的长期记忆需要被有效检索才能发挥作用。检索基于语义相似性而非关键词匹配，系统理解你的查询意图，从记忆库中找到最相关的内容。当用户提问时，系统会分析查询并从长期记忆中检索相关信息，补充到上下文中。例如，如果你问「上次讨论的那个数据库方案是什么」，系统能够检索到相关记忆并提供答案。检索结果会标注来源和置信度，让你了解信息的可靠性。可以使用 `memory search <query>` 命令手动搜索记忆库。记忆还可以被有意识地激活，在新会话开始时使用 `memory load <topic>` 命令将相关记忆加入上下文。合理利用长期记忆可以大大提升 Agent 对你的理解程度和工作效率。

### 4.4 记忆的导入导出

记忆库可以像会话一样导出和导入，便于备份、迁移或分享。导出记忆使用 `memory export` 命令，可以选择导出全部记忆或指定类别的记忆。导出的格式是结构化的 JSON 文件，包含记忆内容、标签、创建时间和来源会话等信息。导入使用 `memory import` 命令，系统会验证导入数据的有效性并合并到现有记忆库。导入时可以选择覆盖同名记忆或保留两份副本。团队场景中，可以共享记忆文件来实现知识传递，但要注意敏感信息的处理。记忆的版本控制追踪每次变更，允许在必要时回退到之前的版本。定期导出记忆作为备份是良好的习惯，可以在系统故障时恢复宝贵的知识积累。

## 五、高级配置与自定义

### 5.1 压缩策略配置

压缩策略的参数可以根据需求精细调整。在配置文件中，可以设置压缩触发的阈值，例如当上下文使用达到 80% 时触发压缩。压缩比例决定每次压缩释放多少空间，较高的比例可以更持久地使用上下文，但可能丢失更多细节。摘要长度控制压缩后摘要的详细程度，较短的摘要节省更多空间但可能遗漏细节。保留策略定义压缩时优先保留什么类型的内容，例如优先保留包含决策、结论或特定关键词的消息。自定义策略可以通过编写策略类实现，定义自己的压缩逻辑。策略可以针对不同场景设置，例如代码审查会话可能需要保留更多代码相关内容。测试不同策略的配置，找到最适合你使用模式的方式。

### 5.2 存储后端配置

记忆存储支持多种后端方案以适应不同需求。本地文件系统是最简单的方案，存储在配置目录下的指定文件夹中，适合个人使用。SQLite 数据库方案提供更好的查询性能和数据完整性保证，适合中等规模的数据。远程存储方案（如 S3、Azure Blob Storage）支持跨设备同步，适合多设备使用场景。配置存储后端时需要指定连接参数、认证信息和路径等。存储加密可以保护敏感数据的安全，使用指定密钥对存储内容进行加密。存储清理策略设置何时自动清理旧数据，防止存储无限增长。备份策略配置定期自动备份记忆数据到指定位置。后端切换时系统会尝试迁移已有数据，确保平滑过渡。

### 5.3 检索增强配置

检索系统也支持多种配置选项来优化检索效果。嵌入模型（Embedding Model）决定如何将文本转换为向量表示，不同的嵌入模型在语义理解能力上有所差异。相似度算法选择使用余弦相似度、欧氏距离还是其他算法计算相关性。检索数量限制控制每次检索返回的结果数量，过多可能稀释相关性高的结果，过少可能遗漏有用信息。过滤规则可以基于标签、来源或时间范围过滤检索结果。混合检索结合关键词匹配和语义检索的优点，提供更全面的检索结果。缓存设置决定是否缓存频繁查询的检索结果，加快响应速度。这些配置影响检索的准确性、速度和资源消耗，需要根据实际使用情况调整。

### 5.4 自定义记忆类型

除了默认的记忆类型，还可以定义自定义的记忆类型来满足特定需求。例如，定义「项目」记忆类型来存储项目相关的信息，包括技术栈、团队成员、关键日期等。定义「偏好」记忆类型专门存储用户偏好，如编程语言偏好、沟通风格偏好等。定义「概念」记忆类型存储学到的术语和概念解释。定义「联系人」记忆类型存储与之交互的人物的相关信息。自定义记忆类型需要在配置中声明其结构和字段，然后就可以像使用内置记忆类型一样使用它们。自定义类型支持字段验证，确保存储的数据符合预期的结构。这使得记忆系统更加灵活，可以适应各种垂直领域的特殊需求。

## 六、最佳实践与案例

### 6.1 高效使用记忆系统的建议

合理使用记忆系统可以显著提升使用体验。首先，尽早建立长期记忆，在开始新项目或领域时就开始记录关键信息，而非等到需要时再追溯。其次，保持记忆的时效性，定期审查和更新存储的记忆，删除过时信息。给记忆打上清晰的标签和描述，便于后续检索和组织。建立良好的命名习惯，使用描述性的会话名称和记忆标题。善用会话归档功能，不常用但需保留的会话移到归档存储。定期导出重要数据作为备份。在团队协作场景中，建立共享记忆库来传递知识和标准做法。关注上下文状态，在接近限制前主动进行维护。理解和选择合适的压缩策略，让系统在保持对话质量的同时最大化利用上下文空间。

### 6.2 典型使用场景

让我们看几个典型场景中记忆系统的应用。第一个场景是长期项目支持：在数周的项目开发中，每次对话都可以参考之前的技术决策、代码约定和已解决的问题，记忆系统让 Agent 能够持续跟进项目状态。第二个场景是个人知识库建设：将学习到的重要概念、常见问题解决方案记录到长期记忆中，后续遇到类似问题可以快速检索和应用。第三个场景是多项目并行处理：同时处理多个项目时，每个项目有独立的会话和上下文，互不干扰，项目间切换时之前的上下文不会影响新的项目。第四个场景是客户服务对话：记录客户的基本信息、历史问题和解决方案，当客户再次联系时可以快速了解背景并提供个性化服务。

### 6.3 常见问题与解决

记忆系统使用中可能遇到一些常见问题。上下文限制频繁触发说明对话太长或压缩过于激进，考虑增加压缩阈值或使用更长的上下文模型。检索结果不相关可能是因为记忆缺乏标签或描述不清晰，改善记忆的元数据可能有效。记忆数据丢失需要检查存储后端的连接和权限配置，以及是否有过期的清理策略。压缩后丢失重要信息可以通过调整保留策略来解决，优先保留包含特定关键词或决策的内容。会话加载慢可能是因为会话太大，检查并清理不需要的长会话。记忆与对话混淆说明需要明确区分需要长期保留的内容（存入长期记忆）和只需短期使用的内容（保留在会话中）。定期检查和维护记忆系统可以预防大多数问题。
