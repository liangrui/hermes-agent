# Hermes Agent 使用指南 02：基础配置篇 - 配置文件与系统设置

## 一、配置系统架构

### 1.1 分层配置机制概述

Hermes Agent 采用了精心设计的分层配置机制，这一机制的核心在于平衡系统默认行为与用户个性化需求之间的关系。整个配置系统可以分为四个主要层次，每个层次都有其特定的作用域和优先级。最高层是命令行参数，它们拥有最高的优先级，能够直接覆盖其他所有配置，通常用于临时修改或调试场景。第二层是环境变量，通过 `HERMES_` 前缀的环境变量可以影响运行时行为，这种方式特别适合容器化部署和自动化脚本。第三层是配置文件，包括用户级配置文件和项目级配置文件，前者位于用户主目录下，后者位于项目或当前工作目录中。第四层是系统默认配置，这些配置被嵌入到代码中，提供了开箱即用的合理默认值。理解这个层次结构对于正确配置和管理 Hermes Agent 至关重要，它能帮助你在不同场景下选择最合适的配置方式。

### 1.2 配置优先级与覆盖规则

当多个层次的配置同时存在时，Hermes Agent 会按照预定义的优先级规则进行处理。命令行参数具有最高优先级，会完全覆盖其他配置中的同名参数。环境变量的优先级次之，但会覆盖配置文件和默认配置中的设置。在配置文件之间，用户级配置的优先级高于项目级配置，这意味着你可以为不同项目设置不同的配置，同时保持个人偏好设置的一致性。配置覆盖是逐字段进行的，而不是整体替换，这允许你只在需要的地方进行定制，而其他字段则继承次优先级的配置。例如，你可以在项目配置中只修改模型选择，而让其他设置沿用用户级配置。这种精细的控制粒度为用户提供了极大的灵活性。

### 1.3 配置文件格式与位置

Hermes Agent 使用 YAML 格式作为主要的配置表示方式，这种格式既易于人类阅读和编写，也便于程序解析和处理。YAML 的层次结构与配置项的组织方式完美对应，通过缩进和嵌套清晰地表达了配置项之间的关系。用户级配置文件通常位于用户主目录下的 `.hermes` 目录中，主配置文件名为 `config.yaml`。此外，在该目录下还有 `profiles` 子目录用于存放多套配置方案（Profile），`plugins` 子目录用于存放插件配置，以及 `credentials.yaml` 用于存储敏感凭证信息。项目级配置文件可以命名为 `hermes.yaml`、`.hermes.yaml` 或放置在 `.hermes` 子目录中。如果没有找到任何配置文件，系统会使用内置的默认配置，并在首次启动时提示用户进行初始化。

## 二、主配置文件详解

### 2.1 基本配置结构

主配置文件 `config.yaml` 包含了 Hermes Agent 运行所需的所有基本设置。文件采用 YAML 格式，支持注释（以 `#` 开头）和多行字符串。整个配置文件的顶层结构包括 `general`（通用设置）、`model`（模型配置）、`tools`（工具配置）、`plugins`（插件配置）、`security`（安全设置）、`logging`（日志配置）等主要部分。每个部分下又包含具体的配置项，采用键值对的形式定义。配置项的命名遵循清晰的语义化原则，通过名称就能大致理解其作用。对于布尔类型的配置项，可以使用 `true/false`、`yes/no` 或 `1/0` 等多种表示方式。对于列表类型的配置项，可以使用行内格式或块格式编写。

### 2.2 通用设置配置

`general` 部分包含了影响 Hermes Agent 整体行为的通用设置。`language` 字段用于指定界面语言，目前支持中文和英文等多种语言。`theme` 字段控制终端界面的主题风格，包括浅色、深色和跟随系统等多种选项。`auto_save` 字段决定是否在退出时自动保存状态，设置为 `true` 可以确保对话状态不会丢失。`max_history` 字段限制保留的对话历史数量，可以根据存储空间和性能需求进行调整。`startup_message` 字段可以设置启动时显示的欢迎信息，支持使用模板变量插入动态内容。`keyboard_shortcuts` 部分允许用户自定义快捷键映射，将常用命令绑定到更方便的按键组合上。

### 2.3 模型配置详解

`model` 部分定义了与 AI 模型交互相关的参数。`provider` 字段指定使用的模型提供商，如 `openai`、`anthropic`、`google` 等。`model_name` 字段指定具体的模型名称，不同提供商有不同的模型命名规范。`api_base` 字段用于配置 API 端点地址，在使用代理或自建服务时特别有用。`api_key` 字段存储 API 密钥，虽然可以直接写在配置文件中，但更安全的做法是使用环境变量或凭证文件引用。`temperature` 和 `top_p` 等采样参数控制生成内容的多样性和创造性。`max_tokens` 限制单次响应的最大长度，`timeout` 设置请求超时时间。`retry` 配置部分定义了重试策略，包括最大重试次数、重试间隔和退避算法等。

### 2.4 工具与插件配置

`tools` 部分控制工具系统的行为。`enabled` 字段是一个布尔值，用于全局启用或禁用工具功能。`allowed_categories` 定义允许使用的工具类别，如 `file`、`web`、`code` 等。`blocked_tools` 列出明确禁用的特定工具。`tool_timeout` 设置单个工具执行的最大超时时间。`confirm_before_execute` 启用执行前的确认提示，增加安全性。`plugins` 部分管理与插件相关的配置，每个插件可以在此部分拥有自己的配置块。插件配置通常包括 `enabled` 开关、插件特定的参数设置以及与主系统的集成选项。某些复杂的插件可能需要额外的配置项，具体可以参考各插件的文档说明。

## 三、环境变量配置

### 3.1 环境变量基础

环境变量提供了一种便捷的配置方式，特别适合容器化部署、持续集成和自动化脚本等场景。Hermes Agent 通过 `HERMES_` 前缀识别自己的环境变量，后续部分对应配置项的完整路径，使用双下划线作为层级分隔符。例如，`HERMES_MODEL__PROVIDER` 对应配置文件中 `model.provider` 字段的值。这种命名约定确保了环境变量与配置文件项之间有一对一的关系，避免了歧义。使用环境变量的优势在于可以在不修改配置文件的情况下调整行为，这对于需要频繁切换配置或在不同环境中部署的情况特别有价值。环境变量通常在 shell 配置文件中设置，也可以通过 `export` 命令在当前会话中临时设置。

### 3.2 常用环境变量列表

以下是一些最常用的环境变量及其对应的配置功能。API 密钥相关的环境变量包括 `HERMES_MODEL__API_KEY`，用于指定模型提供商的访问密钥。`HERMES_MODEL__PROVIDER` 可以快速切换模型提供商而无需修改配置文件。`HERMES_GENERAL__LANGUAGE` 用于设置界面语言。`HERMES_LOGGING__LEVEL` 控制日志详细程度，支持 `DEBUG`、`INFO`、`WARNING`、`ERROR` 等级别。路径相关的环境变量包括 `HERMES_HOME`，可以自定义配置文件的根目录位置。`HERMES_DATA_DIR` 指定数据存储目录，包括会话历史、缓存等。凭证相关的环境变量遵循 `HERMES_CREDENTIALS__` 前缀规范，用于存储敏感信息如 API 密钥、数据库密码等。

### 3.3 环境变量与配置文件的组合使用

在实际应用中，环境变量和配置文件通常会组合使用以达到最佳效果。一个常见的模式是在配置文件中定义稳定的配置项，而使用环境变量覆盖那些需要频繁变化或敏感的设置。例如，你可以在 `config.yaml` 中配置好工具列表、日志级别和界面偏好，而在环境变量中设置 API 密钥。这种方式既保证了配置的可维护性（结构化的配置文件易于阅读和修改），又确保了安全性（敏感信息不会出现在配置文件中）。另一个实用的技巧是使用 `.env` 文件配合支持 dotenv 的启动脚本，可以将所有环境变量集中管理，类似于许多现代应用的做法。Hermes Agent 在启动时会自动检查并加载 `.env` 文件（如果存在），简化了环境配置的管理。

## 四、Profile 配置管理

### 4.1 什么是 Profile

Profile 是 Hermes Agent 提供的一种配置方案管理机制，允许用户创建、保存和快速切换多套不同的配置组合。在日常使用中，你可能需要根据不同场景使用不同的配置：工作时需要一个严谨、保守的配置，休闲时则可以使用更灵活的设置；对于不同类型的任务，可能需要不同的模型选择或工具组合。Profile 机制完美地解决了这一需求，你不需要维护多份独立的配置文件或频繁手动修改配置，而是通过 Profile 在不同方案之间轻松切换。每个 Profile 都是一个完整的配置快照，包含了你选择包含的所有配置项，切换时会完整应用新的配置。

### 4.2 创建与编辑 Profile

创建新的 Profile 有多种方式。最直接的方法是使用命令 `hermes profile create <profile_name>`，这会基于当前配置创建一个新的 Profile。你也可以指定一个现有的 Profile 作为模板，通过 `--from <template_name>` 参数复制其配置。在创建 Profile 时，可以使用 `--set` 参数同时设置特定的配置项，例如 `hermes profile create work --set model.provider=anthropic model.model_name=claude-3`。编辑 Profile 同样简单，使用 `hermes profile edit <profile_name>` 会打开默认编辑器让你修改配置。Profile 的配置文件保存在 `~/.hermes/profiles/` 目录下，文件名与 Profile 名称对应（添加 `.yaml` 后缀）。你也可以直接编辑这些文件进行高级定制。

### 4.3 Profile 切换与激活

切换活动 Profile 只需执行 `hermes profile use <profile_name>` 命令即可。如果不记得 Profile 的名称，可以使用 `hermes profile list` 查看所有已创建的 Profile，以及它们的基本信息如创建时间和描述。通过 `hermes profile info <profile_name>` 可以查看某个 Profile 的完整配置内容。默认 Profile 是系统启动时自动激活的配置，你可以通过 `hermes profile set-default <profile_name>` 命令更改默认 Profile。在某些情况下，你可能需要临时应用某个 Profile 的配置但不改变默认设置，这时可以使用 `hermes profile activate <profile_name>` 命令，激活后的配置只在当前会话有效，会话结束后自动恢复默认 Profile。

## 五、高级配置技巧

### 5.1 条件配置与模板

Hermes Agent 支持在配置文件中使用简单的条件逻辑和模板变量，实现更动态的配置行为。模板变量以 `${}` 的形式嵌入配置中，在运行时会被替换为实际值。内置的模板变量包括 `${env.HOME}`（用户主目录）、`${env.USER}`（当前用户名）、`${date}`（当前日期）和 `${time}`（当前时间）等。通过条件表达式，你可以根据环境或平台有条件地应用配置，语法为 `${if condition:value}` 或 `${if condition:value:else_value}`。例如 `${if env.OS==windows:C:\\Users\\${env.USER}:/home/${env.USER}}` 可以根据操作系统选择不同的路径。这种机制使得同一份配置文件可以在不同环境下正常工作，大大简化了跨平台部署的复杂度。

### 5.2 配置继承与包含

为了减少配置重复和便于维护，Hermes Agent 支持配置的继承与包含机制。在 Profile 配置中，可以使用 `extends` 字段指定一个父 Profile，继承其所有配置并在此基础上进行覆盖。这对于创建具有共同基础配置的多个 Profile 特别有用，避免了复制粘贴带来的维护负担。另一个强大的特性是配置包含，使用 `include` 字段可以将其他配置文件的内容引入当前配置。被包含的文件可以是相对路径（相对于当前配置文件）或绝对路径。例如，你可以将所有敏感的 API 密钥配置放在单独的 `secrets.yaml` 文件中，然后在主配置中通过 `include: secrets.yaml` 引入。这种模块化的配置组织方式既安全又清晰。

### 5.3 动态配置刷新

Hermes Agent 支持在运行时动态刷新配置，无需重启进程即可应用配置变更。这对于生产环境特别有价值，可以在不中断服务的情况下调整系统行为。动态配置刷新有多种触发方式：发送特定的信号（如 `SIGHUP`）给进程、使用管理命令 `hermes config reload`，或者通过 API 端点（如果启用了管理接口）触发。配置刷新是智能的，只会重新加载变更的部分，未变更的配置保持不变。同时，系统会验证新配置的有效性，如果发现语法错误或无效值，会拒绝加载并保留旧配置，确保持续可用性。需要注意的是，某些配置项（如端口号、监听地址等）可能需要完全重启才能生效，这类配置在文档中会有明确标注。

## 六、配置验证与调试

### 6.1 配置验证命令

为了确保配置的正确性，Hermes Agent 提供了 `hermes config validate` 命令来验证配置文件的语法和逻辑。这个命令会检查 YAML 格式是否正确、必填字段是否存在、字段类型是否匹配以及值是否在有效范围内。对于发现的每个问题，命令会报告具体的文件和行号，以及问题的详细描述。除了语法检查，命令还会进行语义验证，例如检查引用的 Profile 是否存在、指定的模型名称是否有效等。验证通过后，会显示一个配置摘要，包括主要配置项的当前值，方便你确认配置已按预期加载。在修改配置后、启动服务前运行验证命令，可以避免因配置错误导致的启动失败或运行时问题。

### 6.2 配置比较与差异分析

当你维护多套配置或需要在不同 Profile 之间切换时，了解配置之间的差异非常重要。Hermes Agent 提供了 `hermes config diff` 命令来比较两个配置或 Profile 之间的差异。默认情况下，命令会比较当前活动配置与指定的 Profile，使用 `--from` 和 `--to` 参数可以指定任意两个配置源进行比较。比较结果以统一的格式展示，新增的配置项标记为绿色、删除的标记为红色、修改的标记为黄色，每个差异项都附带有具体的旧值和新值。这个功能对于审计配置变更、排查问题原因或只是在不同 Profile 间做选择都非常有用。你也可以将差异输出保存为文件，便于后续参考或进行变更追踪。

### 6.3 配置导出与导入

配置导出功能允许你将当前配置或指定 Profile 导出为独立的文件，便于备份或迁移到其他机器。使用 `hermes config export [profile] [--output file]` 命令可以将配置导出为 YAML 格式的文件。导出的文件包含了所有必要的配置项，即使在目标系统上不存在相同的 Profile 也能正常工作。如果不指定 Profile 参数，默认导出当前活动配置。对于敏感信息（如 API 密钥），导出时会有特殊处理：如果是引用环境变量的形式会保留原样，如果是直接写在配置文件中的明文则会提示是否需要脱敏处理。导入功能使用 `hermes config import <file>` 命令，可以将导出的配置文件恢复到系统中，支持同时导入为新的 Profile 或覆盖现有配置。

## 七、配置最佳实践

### 7.1 安全配置建议

安全是配置管理中不可忽视的重要方面。首先，敏感信息如 API 密钥、数据库密码等不应该直接写在配置文件中，而应该使用环境变量引用或存储在专门的凭证文件中。Hermes Agent 的凭证文件采用加密存储，即使文件被非法访问也不会直接泄露敏感信息。其次，生产环境的配置应该遵循最小权限原则，只启用确实需要的功能，禁用不需要的工具和插件。日志配置中应避免记录敏感信息，或确保日志文件的访问权限正确设置。再者，定期更新和轮换 API 密钥，不要使用永久的访问凭证。最后，在团队协作场景中，应该使用版本控制系统管理配置文件，并建立配置变更的审核流程。

### 7.2 性能优化配置

正确的配置可以显著提升 Hermes Agent 的性能。内存相关的配置包括 `cache_size`（缓存大小）和 `max_history`（历史记录数量），根据可用内存合理调整这些值可以平衡性能和资源占用。对于使用远程 API 的场景，`connection_pool_size` 控制并发连接数，`timeout` 设置合理的超时时间可以避免请求无限等待。在工具执行方面，`tool_timeout` 设置合适的工具执行超时，`parallel_tools` 允许某些工具并行执行以提高效率。如果你的系统有多个 CPU 核心，可以调整 `worker_threads` 来充分利用硬件资源。建议在调整这些参数时逐一进行，并用基准测试验证效果，避免盲目优化。

### 7.3 组织与管理建议

良好的配置组织可以大大提升可维护性和协作效率。我们建议将配置分解为多个层次：基础配置放在系统级文件中，包含大多数稳定不变的设置；环境相关的差异化配置通过 Profile 管理；敏感和频繁变更的信息通过环境变量或凭证文件处理。定期审查配置，删除不再使用的过时设置和不必要的自定义项。为主配置和每个重要 Profile 添加描述注释，说明其用途和适用场景。在团队中使用配置模板（Profile）来标准化开发环境，确保所有成员使用一致的配置基础。最后，建立配置变更的文档记录，包括变更时间、变更内容和变更原因，便于追踪和回溯。

## 八、总结

本篇我们深入探讨了 Hermes Agent 的配置系统，从分层配置机制的基本原理开始，详细介绍了配置文件的位置、格式和各项配置的具体作用。我们学习了如何通过环境变量进行便捷的配置覆盖，以及 Profile 机制如何帮助管理多套配置方案。高级配置技巧部分展示了条件逻辑、模板变量和配置继承等强大功能，帮助你构建更灵活和可维护的配置体系。配置验证、比较和导入导出功能则提供了完善的配置管理工具链。最后，我们给出了安全、性能和组织方面的最佳实践建议。掌握这些配置知识后，你应该能够根据不同需求灵活定制 Hermes Agent 的行为。下一篇我们将学习如何使用 Hermes Agent 的交互界面，包括命令行操作和图形界面使用技巧。
